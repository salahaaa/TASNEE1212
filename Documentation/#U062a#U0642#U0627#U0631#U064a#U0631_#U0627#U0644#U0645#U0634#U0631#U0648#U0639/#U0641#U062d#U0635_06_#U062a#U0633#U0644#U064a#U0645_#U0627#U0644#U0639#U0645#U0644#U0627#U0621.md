## 🔴🔴 D1 — بوابة الجودة **لا تعمل إطلاقاً** لأن الواجهة تمرّر `orderId = null` — **مُثبت من طرف إلى طرف**

**بوابة الجودة في `Approve`:**
```csharp
if (dlv.OrderId is int gateOrderId)          // ← إن كان OrderId فارغاً، الفحص كله يُتخطّى
{
    var qualityApproved = Db.QualityChecks.Any(c => c.OrderId == gateOrderId && c.IsApproved);
    if (!qualityApproved) return OpResult.Fail("⛔ لا يمكن التسليم للعميل: فحص الجودة لم يُعتمد بعد…");
}
```

**وما تمرّره الواجهة (`DeliveryView.Save`):**
```csharp
var r = svc.Save(_currentCustomerId, (DateBox.SelectedDate ?? DateTime.Now).ToString("dd/MM/yyyy"), null, …);
//                                                                                             ↑ orderId = null دائماً
```

**الاختبار** — دفعة قرار جودتها **مرفوض**، سُلّمت كما تفعل الشاشة تماماً:
```
quality: Decision=Rejected, IsApproved=True
WFG stock for customer: 1000 kg / 100 cartons

Save(orderId=null) -> Ok = True   تم حفظ سند تسليم العميل CD-2026-0001.
Approve            -> Ok = True   تم اعتماد التسليم وخصم 1,000.0 كجم من رصيد العميل.

   delivery OrderId = NULL   IsApproved = True
   WFG balance after = 0 kg   (الدفعة المرفوضة غادرت المصنع)
```

### السلسلة الكاملة — أربع حلقات، كلها مفتوحة
| # | الموضع | ما يحدث |
|---|---|---|
| 1 | `ExecutionService.ApproveCheck` | **لا يفحص `Decision` إطلاقاً** — يعتمد المرفوض |
| 2 | `FinishedGoodsService.SaveReceipt` | تشترط **وجود** فحص فقط — ولا حتى `IsApproved` |
| 3 | `DeliveryView.Save` | تمرّر **`orderId = null`** |
| 4 | `CustomerDeliveryService.Approve` | البوابة داخل `if (OrderId is int)` → **لا تُنفَّذ أبداً** |

> **النتيجة:** إصلاح أي حلقة بمفردها لا يكفي. فلو أصلحتَ `ApproveCheck` ليفحص القرار، ولو أصلحتَ شرط `IsApproved`، **لما تغيّر شيء** — لأن `OrderId` فارغ فالبوابة لا تُستدعى أصلاً. **الإصلاح يجب أن يكون في الحلقة 3 و4 معاً.**

## 🔴 D2 — الفوترة غير قابلة للوصول: خدمة كاملة بلا شاشة

`PlanProgressService.MarkInvoiced(deliveryId, qty)` **مكتوبة ومحمية بشكل سليم**:
```csharp
Require("delivery", "Post");
if (!d.IsApproved) return OpResult.Fail("السند غير معتمد.");
double remainingBillable = d.TotalQtyKg - d.InvoicedQtyKg;
if (qty > remainingBillable + 0.001)
    return OpResult.Fail($"الكمية أكبر من المتاح للفوترة — المتبقي غير المفوتر: {remainingBillable:N1} كجم (ممنوع تكرار الفوترة…).");
d.InvoicedQtyKg += qty;
```

## 🔴 D3 — `Save` لا يفرض اتساق الكرتون/الكيلو

كل المراحل الأخرى تستدعي `UnitsPolicy.EnsureCartonKgConsistency` (الخطة · الأمر · الإقفال · استلام التام). أما `CustomerDeliveryService.Save` ففيها **`RequireItemType` فقط**:
```csharp
UnitsPolicy.RequireItemType(Db, it.ProductId, "Finished", "تسليم العميل");
dlv.Items.Add(new CustomerDeliveryItem { … PackageCount = it.PackageCount, QtyKg = it.QtyKg });
```
← **سلسلة الوحدات تنكسر عند آخر مرحلة**، فيمكن حفظ سند بكراتين وكجم غير متسقين.

وكذلك `CustomerDeliveryItem` **بلا `CartonWeightKg` مُثبَّت** — بخلاف `FinishedGoodsReceiptItem` و`PlanClosingItem` اللذين يلتقطان وزن الكرتون وقت العملية.

## 🟠 D4 — `Unapprove` يحذف حركات المخزون بدل عكسها
```csharp
Db.InventoryTransactions.RemoveRange(...Where(t =>
    t.ReferenceDocType == ReferenceDocType.CustomerDelivery && t.ReferenceDocNumber == dlv.DocumentNumber));
```
**أفضل من مرحلة التام** (مطابقة تامة `==` لا `StartsWith`، فلا تصادم بادئات) — لكنه ما زال **حذفاً من دفتر الأستاذ**، يناقض قرارهم #48 («إلحاقي غير قابل للتعديل 🔒»).

ومعه `if (bal != null) { … }` — إن لم يُعثر على صف الرصيد تُحذف الحركات **دون إعادة الكميات**، بصمت.
