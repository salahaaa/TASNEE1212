# فحص معمّق — أوامر الإنتاج (MRPMPS1007)
### نزول الأمر من الخطة · الخطة الطويلة · الحقول الزائدة

**الملفات:** `OrdersView.xaml` (143) · `OrdersView.xaml.cs` (538) · `OrdersWindows.cs` (802) · `ProductionOrderService.cs` (925)

## 1) كيف ينزل الأمر من الخطة
```
_planBox (خطط معتمدة وغير مقفلة وغير ملغاة)
   └─ SelectionChanged → LoadItems() → GetOrderableItems(planId)
        └─ يقترح الوردية من أول بند (SuggestedShiftId)
[💾 حفظ وإنشاء] → Create()
   └─ GroupBy(CustomerId) → SaveOrder لكل عميل   (الملكية محفوظة ✅)
   └─ أو ☑ «وزّع تلقائياً» → أمر لكل وردية
```

## 2) 🔴 الخطة الطويلة: كل البنود تنزل معاً… والتواريخ تُهمَل

| الحقيقة | الدليل |
|---|---|
| `GetOrderableItems` يحمّل **كل بنود الخطة بلا فلتر تاريخ** | `Where(i => i.PlanId == planId)` — لا شرط على `ScheduledDate` |
| **الـ Backend يرسل تاريخ كل بند** | `OrderableItemDto.ScheduledDate = pi.ScheduledDate?.ToString("dd/MM/yyyy")` |
| **والواجهة تتجاهله** | `ItemRowUi` لا يحتوي حقل تاريخ، والشبكة **بلا عمود تاريخ** |
| تاريخ الأمر **مفرد** لكل البنود | `Create()`: `string date = _date.SelectedDate.Value.ToString("dd/MM/yyyy")` |
| والافتراضي = **اليوم** لا تاريخ البند | `Init()`: `_date.SelectedDate = DateTime.Today` |
| التوزيع التلقائي على **الورديات لا الأيام** | `GetOrderSlot(..., shId, lineId, date)` — نفس `date` |
| والرسالة تعترف بالقصور | «⚠ لم تتسع ورديات يوم … أضف **يوماً آخر** أو قلّل الكمية» |
| `SaveOrder` **لا يتحقق** من التاريخ مقابل فترة الخطة ولا مقابل `ScheduledDate` للبند | لا `StartDate`/`EndDate`/`ScheduledDate` في `SaveOrder` |

> **النتيجة:** خطة من 14 يوماً بعملاء مجدولين في أيام مختلفة ← تنزل بنودها **كلها في شبكة واحدة بلا عمود تاريخ** ← كلها تأخذ **تاريخ اليوم** (أو التاريخ المفرد المختار) ← **جدولة الخطة تُهدر عند إصدار الأمر**.

## 3) 🟡 الحقول الزائدة في شبكة البنود (14 عموداً، عرض إجمالي **1,475 px**)

| # | العمود | الحكم |
|---|---|---|
| 1‑6 | اختيار · العميل · الدفعة · الصنف المستلم · المنتج النهائي · العبوة | ✅ ضرورية |
| 7‑9 | المخطط (كرتون) · أوامر سابقة (كرتون) · المتبقي (كرتون) | ✅ |
| **10‑12** | **المخطط (كجم) · أوامر سابقة (كجم) · المتبقي (كجم)** | 🟡 **زائدة** — = الكراتين × وزن الكرتون |
| 13 | كراتين الأمر * (قابل للتحرير) | ✅ |
| 14 | الوزن المكافئ (كجم) | ✅ مشتق ومطلوب |

**الدليل من تعليق الكود نفسه:**
```csharp
// §طلب المستخدم: المخطط بالكرتون كما في الخطة — أعمدة الكراتين أولاً ثم الكجم
```
فأعمدة الكراتين **أُضيفت فوق** أعمدة الكجم دون حذفها. وقاعدة الشاشة المعلنة: *«الكراتين هي وحدة الأمر الأساسية، والكجم وزن مكافئ للقراءة فقط»* — أي أن الأعمدة 10‑12 تكرار لما تعرضه 7‑9 بوحدة أخرى.

**ملاحظات إضافية:**
- عمود «العبوة» يدمج الاسم والوزن في نص واحد: `"كرتون = 10.0 كجم/كرتون"` ← لا يمكن الفرز أو الفلترة بالوزن.
- زر «⬇ إنزال بنود الخطة» **مكرر وظيفياً** — `_planBox.SelectionChanged += LoadItems` يُنزّل تلقائياً؛ وقيمته الوحيدة `if (_plans.Count == 0) Init()`.
- **العمود الناقص الأهم: التاريخ المجدول** — متاح من الـ Backend ومُهمَل في الواجهة.

## 4) ✅ ما هو صحيح في هذه الشاشة (إنصاف)

| البند | الدليل |
|---|---|
| **لا ثغرة تجاوز داخل المستند الواحد** | `CheckPlanRemaining` يستثني الأمر الحالي فقط: `x.OrderId != order.Id` — **بخلاف علّة شاشة الخطط** |
| فحص الطاقة في الـ Backend | `CheckOrderCapacity(order)` |
| حراس الهوية | مطابقة صنف بند الخطة (`IDENTITY_MISMATCH`) · منع دفعة عميل آخر (`CROSS_CUSTOMER`) · `ProductIdentityGuard` · `UnitsPolicy.RequireItemType` |
| **وزن الكرتون مُثبَّت وقت العملية** | `CartonWeightKg = UnitsPolicy.CartonWeight(...)` — «لا يتغير بتعريف العبوة لاحقاً» ✅ |
| العبوة تنتقل للأمر | `PackagingTypeId = dto.PackagingTypeId` — الفجوة السابقة أُغلقت |
| أمر لكل عميل | `GroupBy(r => r.Src.CustomerId ?? 0)` — الملكية محفوظة |
| أمر لكل وردية عند التوزيع التلقائي | مع رسالة صريحة بالمتبقي الذي لم يتسع |
