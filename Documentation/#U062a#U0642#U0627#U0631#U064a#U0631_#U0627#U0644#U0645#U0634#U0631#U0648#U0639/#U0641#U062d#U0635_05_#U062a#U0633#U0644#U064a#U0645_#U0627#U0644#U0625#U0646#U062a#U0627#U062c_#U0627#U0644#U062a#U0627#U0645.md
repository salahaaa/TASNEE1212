# فحص معمّق — تسليم الإنتاج التام: الإصدار والاستلام (MRPMPS1015)

**الملفات:** `FinishedGoodsView.xaml` (99) · `FinishedGoodsView.xaml.cs` (392) · `FinishedGoodsService.cs` (223) · `Delivery.cs` (58)

**الدورة القانونية المعلنة:** أمر التسليم ← الإصدار للمخزن (**بلا أثر على الأرصدة**) ← سند الاستلام المخزني (**وحده يحرّك أرصدة WFG**). وهذا التصميم **صحيح وسليم**.

## 🔴🔴 FG1 — بوابة الجودة في الخدمة لا تشترط الاعتماد أصلاً — **مُثبت بالتشغيل**

```csharp
// FinishedGoodsService.SaveReceipt — الفحص الوحيد هو «الوجود»
var qualityCheck = Db.QualityChecks.AsNoTracking()
    .Where(c => c.OrderId == orderId).OrderByDescending(c => c.Id).FirstOrDefault();
if (qualityCheck == null)
    return OpResult.Fail("لا يمكن تسليم الإنتاج قبل إقفال يوم الإنتاج وإرساله إلى الجودة…");
bool coolingPending = !qualityCheck.IsApproved;      // ← تُستخدم في نص الرسالة فقط
```

**الاختبار** — فحص جودة **محفوظ وغير معتمد**:
```
quality check saved, IsApproved = false
SaveReceipt with an UNAPPROVED quality check -> Ok = True
   تم إنشاء أمر تسليم الإنتاج DLV-2026-0001 — الجودة سمحت بالتسليم للتام.
Issue   -> Ok = True
Receive -> Ok = True   تم الاستلام الكامل وتقييد كامل الكمية في مخزن الإنتاج التام.
```

> **الخدمة أكثر تساهلاً من الواجهة.** فالواجهة (`Load`) تشترط `c.IsApproved`، لكن `SaveReceipt` تشترط **الوجود فقط** — وأي مسار آخر يستدعي الخدمة مباشرة يتجاوز الواجهة كلياً. والرسالة تقول *«الجودة سمحت بالتسليم»* بينما الجودة **لم تسمح بشيء**.

**وهذا الحلقة الثالثة في سلسلة تجاهل قرار الجودة:**
| الموضع | ما يفحصه |
|---|---|
| `ExecutionService.ApproveCheck` | لا يفحص القرار إطلاقاً |
| `CustomerDeliveryService:82` | `IsApproved` فقط |
| **`FinishedGoodsService.SaveReceipt`** | **الوجود فقط — ولا حتى `IsApproved`** |

## 🔴 FG2 — `Unapprove` **يحذف** حركات المخزون بدل عكسها

```csharp
var prefix = rcpt.ReceiptNumber ?? rcpt.DocumentNumber;
Db.InventoryTransactions.RemoveRange(Db.InventoryTransactions.Where(t =>
    t.ReferenceDocType == ReferenceDocType.FinishedGoodsReceipt &&
    t.ReferenceDocNumber.StartsWith(prefix)));
```
**مُثبت:** بعد الإلغاء `inventory txns remaining = 0` — الحركات **مُحت من دفتر الأستاذ**.

| المشكلة | الأثر |
|---|---|
| **الحذف بدل القيد العكسي** | يدمّر دفتر الأستاذ. وهو يناقض قرارهم #48: *«سجل التدقيق: إلحاقي غير قابل للتعديل 🔒»* |
| **`StartsWith(prefix)` تصادم بادئات** | الترقيم `{Prefix}-{yyyy}-{NNNN}` بأربعة أرقام. عند السند رقم 10,000 يصبح `RCV-2026-10000`، و`RCV-2026-1000` **بادئة له** ← إلغاء السند 1000 يحذف حركات السند 10000 |
| **`if (bal != null)`** | إن لم يُعثر على صف الرصيد، يُتخطّى العكس **بصمت** بينما تُحذف الحركات ← الرصيد والدفتر يفترقان |

## 🔴 FG3 — `Unapprove` يعكس الرصيد **بغير** البُعد الذي كُتب به

```csharp
// Receive — يكتب بالعميل
PostStockMovement(whFg, MovementType.Inbound, recv, pkgRecv, …, customerId: orderCust, …);

// Unapprove — يقرأ بلا فلتر عميل
var bal = Db.StockBalances.FirstOrDefault(b =>
    b.WarehouseId == whFg && b.ProductId == item.ProductId && b.LotId == item.LotId);
```
`PostStockMovement` يبحث عن الرصيد **شاملاً `CustomerId`** ويُنشئ صفاً به إن غاب. أما `Unapprove` فيأخذ **أول صف** بلا فلتر عميل ← قد يطرح من **صف آخر** (مثلاً `CustomerId = NULL`) ويترك الصف الصحيح كما هو، أو يدفع صفّاً للسالب.
*(لم يظهر في اختباري لأن هناك صفاً واحداً فقط — فهو خطر كامن يظهر عند تعدد صفوف الرصيد لنفس المخزن/الصنف/الدفعة بعملاء مختلفين، وهو ممكن لأن `StockBalances` **بلا قيد فريد** كما ثبت في الفحص الشامل.)*

## 🟠 FG4 — الإغلاق التلقائي للأمر يعتمد على `PlannedQtyKg` الممحو

```csharp
if (order != null && order.Items.All(i => i.ProducedQtyKg + 0.001 >= i.PlannedQtyKg))
{ order.Status = DocStatuses.Completed; order.IsClosed = true; … }
```
وبما أن `ClosePlanItems` سبق فكتب `oi.PlannedQtyKg = oi.ProducedQtyKg`، فالشرط **صحيح دائماً** ← الأمر يُغلق تلقائياً عند اكتمال الاستلام **بغضّ النظر عن تحقيق الخطة**. نفس الجذر الذي كشفته مرحلة الإقفال.

## 🟠 FG5 — تاريخ الفحص المتوقع يظهر **فارغاً** في رسالة المستخدم

```csharp
$"\n🔬 الفحص النهائي متوقع {qualityCheck.ExpectedCheckDate:dd/MM/yyyy} (فترة تبريد) …"
```
`ExpectedCheckDate` **يُملأ فقط** عند إنشاء الفحص من مسار الإقفال (`ExecutionService.cs:200` و`:454`). أما الفحص المنشأ من شاشة الجودة مباشرة (`SaveCheck`) **فلا يُملأ له إطلاقاً**.

**مُثبت من الاختبار:**
```
🔬 الفحص النهائي متوقع  (فترة تبريد) — تسليم العميل متوقف على اعتماد الفحص.
                     ↑ فراغ
```

## 🟠 FG6 — `qualityCheckId` المُمرَّر لا يُستخدم في التحقق
`SaveReceipt(orderId, qualityCheckId, …)` يبحث عن **أحدث** فحص للأمر متجاهلاً المعامل، ثم يخزّن `qualityCheckId` على السند ← **السند قد يشير إلى فحص غير الذي استُند إليه**.
