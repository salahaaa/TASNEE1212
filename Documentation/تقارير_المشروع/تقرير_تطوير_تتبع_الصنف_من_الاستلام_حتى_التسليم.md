# تقرير التطوير الإلزامي — تتبّع الصنف من الاستلام حتى الإنتاج والفحص والتسليم

**التاريخ:** 2026-08-28 | **الحالة:** مُنفَّذ ومُختبَر آلياً — **77 اختباراً ناجحاً من 77**
**الحزمة:** `DateERP_تحديث_تتبع_الصنف_استلام_حتى_تسليم.zip` (4 ملفات DLL + مجلد Source للاطلاع)

**القاعدة المُنفَّذة:** الصنف المستلم هو هوية المادة التي تستمر مع العملية حتى نهاية الدورة:
**سكري مستلم → سكري تام → فحص سكري تام → مخزون سكري تام → تسليم سكري تام**،
**خلاص مستلم → خلاص تام → فحص خلاص تام → مخزون خلاص تام → تسليم خلاص تام** —
ولا يجوز في أي مرحلة ظهور اسم عام («تمور») بدلاً من الصنف الفعلي، في قاعدة البيانات والـ Backend والواجهات والتقارير معاً.

---

## 1) الجداول التي تم تعديلها

| الجدول | التعديل | الغرض |
|---|---|---|
| `Products` | عمود جديد `SourceProductId` (فارغ = بدون تعريف) | التعريف الرسمي للتحويل: الخام الذي يُنتَج منه المنتج التام (سكري تام ← سكري) |

- المرحّل الشامل `SchemaMigrator` يضيف العمود تلقائياً لأي قاعدة قديمة عند أول تشغيل (بلا حذف بيانات)، ثم **يربط التحويلات آلياً من أسماء الأصناف** («سكري فاخر 1كجم» ← «تمر خام - سكري») حتى لا تنكسر القواعد القائمة.
- لا جداول جديدة؛ كل جداول الدورة كانت تحمل الهوية أصلاً على مستوى الأسطر (انظر البند 2).

## 2) العلاقات التي تم إضافتها أو تعديلها

الهوية كانت محفوظة بنيوياً في كل الجداول — التطوير ثبّتها **بقيود فرض (حراس) في الـ Backend**:

| المرحلة | الجدول/الكيان | عناصر الهوية المحفوظة لكل سطر |
|---|---|---|
| الاستلام | `ShipmentItems` → `Lots` | `ProductId` صريح إلزامي + `CustomerId`؛ كل بند استلام يولّد **دفعة مستقلة** (لا دمج صنفين) |
| الخطة | `ProductionPlanItems` | `ProductId + LotId + ShipmentId + CustomerId` — مرجع كامل لكل سطر |
| أمر الإنتاج | `ProductionOrderItems` | نفس المرجع + `PlanItemId` — الصنف ينتقل حرفياً من بند الخطة |
| الإنتاج الفعلي | `ProductionExecutions` / `PlanClosingItems` | التوزيع على بنود الأمر بصنفها وعميلها |
| الفحص | `QualityCheckItems` | `ProductId + LotId` — فقط أصناف الأمر |
| المخزون | `StockBalances` / `InventoryTransactions` | `(مخزن × صنف × دفعة × عميل)` — لا مخزون عام باسم «تمور تامة» |
| التسليم | `CustomerDeliveryItems` | `ProductId + LotId` — سند واحد **متعدد الأصناف** |
| **جديد** | `Products.SourceProductId` | علاقة تحويل رسمية خام ← تام تُفرض في كل المراحل |

## 3) الـ APIs التي تم تعديلها

| الخدمة/الواجهة | التعديل |
|---|---|
| `ITraceabilityService` **(جديدة)** | `GetJourneys(customerId?, productId?)` و`GetLotJourney(lotId)` — رحلة الصنف كاملة: استلام ← خطة ← أمر ← إنتاج ← فحص ← مخزون ← تسليم ← فاتورة + المتبقي |
| `ProductIdentityGuard` **(جديدة)** | دالة مركزية `EnsureConversionAllowed` يفرضها كل مسار: تحويل مطابق للبطاقة ← مسموح؛ مختلف ← رفض قاطع؛ بلا تعريف ← رفض حتى يُضاف التعريف |
| `IReceivingService.SaveShipment` | إلزامية الصنف الصريح لكل بند + رفض الصنف الموقوف |
| `IPlanningService.SavePlan / UpdatePlan` | فرض التحويل الرسمي عند الربط بدفعة |
| `IProductionOrderService.SaveOrder` | فرض التحويل + **مطابقة صنف الأمر لصنف بند الخطة** (رفض اختلاف الهوية عند الإصدار) |
| `IQualityService.SaveCheck` | رفض أي صنف ليس من بنود الأمر + فرض التحويل على الدفعة |
| `IFinishedGoodsService.SaveReceipt` | رفض دفعة لا تطابق بند الأمر (`LOT_MISMATCH`) + فرض التحويل |
| `ICustomerDeliveryService.Save` | رفض تسليم صنف من دفعة صنف آخر + إلزامية وجود الصنف في البطاقة |
| `IPlanProgressService.UpdatePlanItem` | **قفل الهوية**: منع تغيير صنف البند بعد وجود عمليات + فرض التحويل للصنف الجديد |
| `MasterDataService.SaveProduct/SaveProductFull` | حقل `sourceProductId` + رفض اسم «تمور/تمر» كصنف خام/تام (فئة فقط) + تحقق أن المصدر صنفاً خاماً |
| `MasterDataService.DeleteProduct/ById` | أي عمليات مرتبطة (استلام/خطط/أوامر/فحص/تسليم/أرصدة) ← **إيقاف بدل الحذف** |
| `IReportService` | تقرير جديد `item_journey` + معاملات تصفية `customer` و`product` لتقارير: الاستلام، الدفعات، الخطط، الأوامر، الإنتاج، الجودة، التام، التسليم |

## 4) الشاشات التي تم تعديلها

| الشاشة | التعديل |
|---|---|
| الأصناف `ProductsView` | حقل «الصنف المصدر (الخام) — التعريف الرسمي للتحويل» + زر «🔍 رحلة الصنف (التتبع الكامل)» + عمود المصدر في الجدول |
| **نافذة رحلة الصنف `TraceabilityWindow` (جديدة)** | جدول الرحلة الكامل (مرحلة/مستند/تاريخ/عميل/صنف/دفعة/كمية/حالة) مع ملخص إجمالي لكل صنف وتصفية بالعميل/الصنف |
| التقارير | التقرير الجديد «تتبع الصنف — الرحلة الكاملة» + حقلا تصفية بالعميل والصنف لكل التقارير التشغيلية |
| الاستلام/الخطة/الأوامر/التنفيذ/الجودة/التام/التسليم | تعرض الاسم الفعلي للصنف من أسطرها (البنية كانت حاملة للهوية أصلاً — الحراس الآن يمنعونه من الوصول لبيانات عامة) |

## 5) قواعد التحقق التي تمت إضافتها (كلها في الـ Backend)

1. **منع التحويل الخاطئ:** إنتاج خلاص من دفعة سكري ← رسالة: «منع تحويل خاطئ: المنتج معرَّف في بطاقته أنه يُنتَج من…». تُفرض في: الخطة، الأمر، الفحص، استلام التام، التسليم.
2. **إلزامية التعريف الرسمي:** منتج تام بلا تعريف مصدر من دفعة خام ← رفض حتى يُحدَّد المصدر في بطاقة المنتج (مع ربط آلي للقواعد القديمة من الأسماء).
3. **قفل الهوية:** تغيير صنف بند خطة بعد وجود إنتاج/فحص/تسليم/أوامر ← رفض مع إرشاد لمسار التعديل/الإلغاء بالصلاحية.
4. **مطابقة الهوية عند الإصدار:** صنف أمر الإنتاج ≠ صنف بند الخطة ← رفض.
5. **فحص غريب:** صنف في الفحص ليس من بنود الأمر ← رفض.
6. **دفعة غريبة:** استلام تام بدفعة غير دفعة بند الأمر ← رفض.
7. **منع الدمج:** كل بند استلام يولّد دفعته المستقلة؛ لا توجد أي عملية دمج في النظام؛ الاستلام بدون صنف صريح مرفوض.
8. **منع الأسماء العامة:** «تمور/تمر/تمور تامة» مرفوضة كأصناف خام أو تامة — تصلح فئة فقط.
9. **منع الحذف المفقِد للتاريخ:** صنف مستخدم ← إيقاف بدل الحذف.
10. **رفض الصنف الموقوف** في الاستلام.
11. **الفوترة على المسلَّم فقط** موزعة على البنود تناسبياً (لا ازدواج في سند متعدد الأصناف).

## 6) نتائج اختبارات سكري وخلاص ✅

| البند | سكري | خلاص |
|---|---|---|
| الاستلام | 10,000 كجم — دفعة مستقلة | 8,000 كجم — دفعة مستقلة |
| الخطة | سكري ← سكري تام 5,000 | خلاص ← خلاص تام 4,000 |
| أمر الإنتاج | نفس الصنف والدفعة والعميل | نفس الصنف والدفعة والعميل |
| الإنتاج الفعلي | 5,000 كجم (داخل سكري فقط) | 4,000 كجم (داخل خلاص فقط) |
| الفحص | ناجح — مقبول 4,950 | ناجح — مقبول 3,950 |
| المخزون التام | 4,950 باسم العميل والصنف | 3,950 باسم العميل والصنف |
| التسليم | 1,000 | 500 |
| الفاتورة | 1,000 (حصة البند من السند) | 500 |
| **المتبقي في الرحلة** | **3,950** | **3,450** |

رحلة كل صنف عُرضت كاملة من واجهة `ITraceabilityService` بمراحلها الثمانية، ولم تظهر كلمة «تمور» في أي مرحلة.

## 7) نتائج اختبار عميل واحد ✅

السيناريو الإجباري البند 17 كاملاً: استلام (سكري 10,000 + خلاص 8,000) → خطة واحدة بالصنفين → أمر إنتاج → إقفال يوم الإنتاج وإرسال للجودة → فحص واعتماد → استلام تام في المخزون → **سند تسليم واحد متعدد الأصناف** → فاتورة → فتح سجل سكري وسجل خلاص وعرض الرحلة الكاملة لكل منهما بالأرقام أعلاه. **ناجح آلياً.**

## 8) نتائج اختبار عدة عملاء ✅

ثلاثة عملاء في **خطة إنتاج واحدة** (5 بنود):
- عميل A: سكري 5,000 + خلاص 4,000 | عميل B: سكري 6,000 + خلاص 3,000 | عميل C: سكري 2,000 (استلام منفصل لكل عميل).
- الحجوزات منفصلة لكل دفعة: سكري A = 3,000 فقط، سكري B = 2,500، سكري C = 1,000 — **لا خلط**.
- تقدم كل عميل مستقل داخل الخطة: A = 5,000 | B = 4,000 | C = 1,000.
- رحلة سكري لكل عميل تعرض أرقامه وحده (5,000 / 6,000 / 2,000).
- محاولة تخطيط دفعة العميل B باسم العميل A ← **مرفوضة**.

## 9) نتائج اختبار أمر تسليم متعدد الأصناف ✅

سند تسليم واحد للعميل A احتوى **سكري تام 1,000 كجم + خلاص تام 500 كجم معاً**، اعتُمد وخصم من رصيد كل صنف على حدة في مخزن التام (لا رصيد عام)، وفُوتر 1,500 كجم موزعة على البندين تناسبياً (1,000 / 500). ومحاولات الخطأ المرتبطة رُفضت: تسليم خلاص بدفعة سكري ← «منع تحويل خاطئ».

## 10) أي نقطة ما زالت تحتاج معالجة

معالَج في هذا التحديث كل ما يخص دورة الهوية. المتبقي من خارطة الطريق (مؤجل باتفاق سابق، لا يمس الهوية):

1. **مرحلة التقارير المتقدمة** (قوالب الطباعة، تقارير يومية/شهرية تفصيلية) — جاهزة خطتها في `خطة_مرحلة_التقارير_المقترحة.md`، والبنية الحالية (تقرير الرحلة + التصفية بالعميل/الصنف) أساس لها.
2. **التقويم/الجدول الزمني البصري للخطة**، وعبور منتصف الليل، وتقسيم البند على أيام — فجوات تشغيلية من الفحص الشامل السابق، لا تؤثر على هوية الصنف.
3. **الاختبار على جهازك:** الرجاء تجربة الحزمة على السيناريو الحقيقي، وإن ظهرت أي رسالة منع غير متوقعة أرسل نصها كاملاً — الرسائل الآن تفصيلية وتوضح الصنفين المعنيين.
